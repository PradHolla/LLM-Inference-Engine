Qwen3-8B · one NVIDIA A10G · every number predicted before it was measured

An inference engine from scratch, and why every speed-up here is a range

Eight parts on one GPU and one model. A performance model built from memory bandwidth and parameter count alone, then a deliberately naive server, then an engine written from scratch, then vLLM — each measured by the same client over the same protocol. Then the same discipline turned on the techniques the field quotes as single numbers: quantization, guessing ahead, and the cache underneath both. Every value was predicted in writing before it was measured, which is the only way a wrong prediction becomes information rather than embarrassment; about a third of them were wrong, and those are the ones worth reading. The recurring finding is that none of these techniques has a number. The same quantization flag is worth 1.07× or 2.35×; the same guessing 1.19× or 2.25×; the same cache nothing or 13.8×. What decides it is never the technique, it is whether anything was pressing against the limit it relieves. The last part turns that lesson on this document and retires one of its own explanations. A final part asks what a reasoning model’s hidden thinking is actually worth, and finds the same answer in a fourth place: on one workload it is worth 0.4 points for eighteen seconds of silence, and the cleverest way to spend it loses to the simplest.

Part one · The problem

Where it starts: a server that serves one person at a time

The first server was built to be bad on purpose. It holds a lock around the whole model: a request arrives, generates all its tokens, releases the lock, and only then can the next one start. That gives a hard ceiling of about one request every three seconds.

The number that mattered wasn't the throughput, though. It was this:

Inter-token latency is flat across a five-fold increase in load while time-to-first-token grows 20×. That is the fingerprint of a queue, not a slow model. The GPU is producing tokens at exactly the same rate throughout; the wait is people standing in line.

So the diagnosis wrote itself: batch-1 decoding was already within 4% of what the hardware physically allows. The problem was capacity, not speed. Serving more people at once, not making one person faster.

Terms used throughout

Three numbers, and why they are never averaged

TTFT — time to first token — is how long you stare at nothing after pressing enter. ITL — inter-token latency — is the gap between tokens once they start, which is how fast text appears to stream. Capacity is the arrival rate above which the queue grows without bound.

All three are reported at p50 / p95 / p99, never as means. An average hides the one-in-twenty user who waited four seconds, and that user is the one who complains. TTFT and ITL are kept separate because they break for different reasons — TTFT degrades from queueing, ITL from the model execution itself. Reporting only end-to-end latency conflates them and hides which one broke.

The one piece of physics everything rests on

Generating a single token requires reading every weight in the model — all 15.26 GiB — out of GPU memory. The arithmetic performed on those weights is trivial by comparison. Decoding is therefore not limited by how fast the GPU computes; it is limited by how fast it can read.

16.4 GB of weights  ÷  600 GB/s of bandwidth  =  27.3 ms per token, floor
measured on this card:                                40.5 ms per token
                                                      → 67% of theoretical peak

And here is the consequence that makes an inference engine worth writing at all: if you process eight requests together, you read those 15.26 GiB once for all eight, not eight times. The expensive part is shared. Only the per-request cache grows with batch size.

Concept

What the KV cache is, and why it sets every limit in this document

When a model generates token 500, it must attend to tokens 1 through 499. Rather than recompute them each step, it stores two vectors per token per layer — the keys and the values. That store is the KV cache.

For this model it works out to 2 × 36 layers × 8 kv-heads × 128 dims × 2 bytes = 147,456 bytes, exactly 144 KiB per token. Every request holds its own. That is why you cannot simply batch a thousand requests: the weights are shared, the cache is not, and the cache is what runs out.

Build the ruler before the thing it measures

Everything above is a number, and a number is only worth as much as the instrument that produced it. So the first work on this project involved no model at all. Three tools were written and proven first, because a benchmark you have not tested is not a measurement, it is a rumour.

roofline.py predicts what the hardware should manage from two facts and nothing else: memory bandwidth and parameter count. bench.py measures what it actually manages. And mock_server.py is a fake server with no model inside it — it imitates a real one badly on purpose, complete with a queue and a capacity ceiling, so the benchmark client could be proven capable of finding a knee before it was ever pointed at a GPU that costs $1.21 an hour.

Only then was the naive server measured, against predictions written down in advance:

Concept

Why the load generator never waits for a reply

The obvious way to benchmark a server is to send a request, wait for the answer, then send the next. That is closed-loop, and it cannot measure capacity. If the server slows down, you send requests more slowly, so a queue can never form — the offered load is throttled by the very latency you are trying to measure. The p95 it reports is fiction.

This benchmark is open-loop: requests are fired at a fixed rate on a random arrival schedule, regardless of whether earlier ones have finished. If the server cannot keep up, the queue grows and the latency numbers show it. Sweep the rate upward and the point where latency turns sharply upward is real capacity. Every capacity number in this document was found that way.

Part two · Writing an engine

RECON

Measure the cache before designing around it

Before any engine code was written

One prediction was carried forward untested: "bf16 dies of KV exhaustion above batch 4 at 4k context." Since the next step was to start batching, that number set the entire design budget. So the first thing built was an instrument that reads the cache off the GPU rather than inferring it.

QuantityPredictedMeasuredVerdict
KV bytes per token147,456 B147,456 Bexact
VRAM growth per decode step147,456 B147,456 Bexact
Batch ceiling at 4k context117missed 36%

The carried claim was wrong in the safe direction — it dies above 7, not 4. "Batch 4" turned out to be an artifact of the prediction tool printing powers of two: it showed rows 1, 2, 4, 8, so 4 was simply the last one that passed. Rows 5, 6 and 7 were never displayed.

Three things were eating memory that nothing had budgeted for

  • Allocator fragmentation — 1.93 GiB, the largest term. PyTorch grows the cache by allocating a slightly bigger block and freeing the slightly smaller one. Every freed block is permanently one size too small for what comes next, so they accumulate. Cost: 0.265 GiB per sequence, 47% of the KV it accompanied.
  • The GPU reports three different "total memory" numbers. Marketing says 24 GB. nvidia-smi says 22.488 GiB. CUDA can actually address 22.060 GiB. The 439 MiB difference is driver reserve, and the prediction tool was budgeting from the wrong one.
  • Activations were underestimated 2×.

One environment variable was worth 29% more concurrency. Setting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True raised the ceiling from 7 to 9 requests, for zero code change. It switches PyTorch to a virtual-memory allocator that extends regions in place instead of leaving a graveyard of wrong-sized blocks.

Take the decode loop away from the library

Static batching, and the waste it exists to reveal

A static batch cannot release a finished sequence.

This is why the instrument was built to report both numbers side by side. Divide by slots and static batching looks solved; divide by tokens anyone received and it is 82% waste. The gap is the entire case for continuous batching, and it is invisible to the flattering metric.

STEP 3

Continuous batching: refill the slot the moment it frees

Evict, admit, decode — every step

The fix is simple to state: every step, drop finished requests and admit queued ones into the freed slots. The difficulty is mechanical. Requests admitted at different times have different lengths, and HuggingFace's cache API assumes one shared position across the batch. That mismatch is precisely why vLLM wrote its own attention kernels.

The workaround

Left-padding, with position decoupled from storage

Put every row in one shared buffer, right-aligned, padding the front of shorter rows. A row's keys and values are rotated by their position at the moment they are written, so where a row physically sits in the buffer does not affect correctness — only the attention mask and the position IDs must be right.

That claim was tested before any engine was built, against single-request references, demanding token-for-token identity. All three mechanics passed: ragged batching, evicting a row mid-decode, and admitting a new row mid-flight.

A failed experiment that taught more than a successful one

Throughput still came in 33% below prediction, because ITL was 61.4 ms where step 2 measured 43.8 ms at the same batch size. Hypothesis: passing an explicit attention mask forces the GPU off its fast path. The test compared a batch with a mask against one without:

static, no mask          44.6 ms

Except the control was broken. Admitting all eight requests at once makes every row the same length — so the mask was all ones. It masked nothing. The experiment had removed the padding along with the thing it was meant to test.

Plotting latency against buffer length over the real run settled it: at a constant 8 active rows, ITL rose 27.4 microseconds per buffer token, against 2.9 predicted by the memory model — 9.4×.

STEP 4

The paged allocator we measured, then chose not to build

A negative result

Step 4 was meant to be a paged allocator — vLLM's central trick, storing the cache in fixed-size blocks with a lookup table so sequences never need contiguous memory. The target was that 27.4 µs-per-token tax.

But the tax had two possible causes pointing in opposite directions, so the first move was to find out which. One experiment, holding batch, buffer length and cache contents fixed, varying only the mask:

ConditionITL p50vs baseline
No mask (implicit causal)43.89 ms1.00×
Explicit mask, all ones — masks nothing43.94 ms1.00×
Explicit mask, real zeros — actually masks54.60 ms1.24×

A mask that masks nothing is free. A mask with real zeros costs 10.7 ms. The tax is the GPU's masked attention path — not reads over padded memory. Which means a paged allocator cannot recover it here: rows of different lengths need a mask however the cache is stored, and a block-based design would still have to gather those blocks into a dense padded tensor to hand the attention kernel.

The fix that does work is varlen attention — FlashAttention's interface that packs ragged sequences with no padding and no mask at all. That is what vLLM pairs with paged storage.

So the conclusion, reached by measurement rather than by reading the paper: PagedAttention's speed is inseparable from the custom CUDA kernel written to consume block tables directly. The allocator is not the clever part — the kernel is. Building the allocator on stock PyTorch would have been an exercise, not an optimisation, and the honest call was to say so rather than ship a component whose measured benefit is zero.

Part three · Measuring vLLM

The baseline, and the trap in it

Swapping in vLLM is an hour's work, and it is faster. That measurement alone teaches nothing — "the library written by specialists beats my two-day engine" is not a finding. The phase is the ablation: turn each technique off, one at a time, and see which part of the gap it was carrying.

First, though, a configuration detail that would have invalidated everything downstream.

Read the log, never the docs

vLLM ships with two of the techniques already on

Its startup log reports enable_prefix_caching=True and enable_chunked_prefill=True. Older releases had both off, so a great deal of writing about vLLM is misleading on exactly this point. Neither our engine nor the baseline has either.

That means "vLLM defaults versus our engine" is not a like-for-like comparison, and the ablations must disable these to isolate them rather than enable them. Assuming the older defaults would have made every attribution in this section confidently backwards.

Concept

Prefix caching, and why our benchmark flatters it

If two requests begin with the same tokens — a shared system prompt, say — their keys and values for that span are identical. Prefix caching stores those blocks once and points both sequences at them, skipping the recomputation entirely.

Our benchmark sends a byte-identical 412-token prompt on every request. That is the perfect-hit case, and it is an artifact we constructed by holding the prompt constant. The honest measurement uses --unique-prefix, which prepends a random header per request and defeats the cache. Both are reported below; only one describes real traffic.

Single stream, one request at a time. ITL is identical either way because prefix caching only touches prefill.

vLLM's single-stream advantage splits cleanly along two independent axes. With the cache defeated its TTFT equals ours within 2%, so the TTFT advantage is entirely prefix caching. Its ITL is 34.0 ms either way against our 41.1, so the ITL advantage is entirely kernel efficiency — and that is measured at batch 1, where no scheduling advantage exists at all.

Back-solved against the 27.30 ms roofline floor, that ITL number revises a conclusion we had already drawn:

We had concluded that 0.674 was "a property of the stack, not the card," and that the naive server's 0.623 was overhead. That was half right. A further 16% was sitting in per-step Python — cache bookkeeping, mask concatenation, argmax, the device-to-host sync — that a CUDA graph removes by replaying the whole step in one launch. That is a third axis, orthogonal to all the scheduling work: not how many requests share a weight read, but how much of the hardware a single step uses.

The ladder, plotted

Each curve is one engine. The x-axis is throughput actually achieved; the y-axis is the latency the slowest 5% of users saw. A curve that runs flat and then turns vertical has hit capacity — past the turn, arrivals outrun service and the queue grows without bound.

Read the vertical distance, not the horizontal. At 0.5 req/s the naive server was already 50% past its own capacity and queueing catastrophically — TTFT p95 of 25.1 seconds. vLLM sits at a third of capacity and barely notices, at 336 ms. Capacity improved 17× end to end; latency at a fixed, realistic load improved by nearly two orders of magnitude.

Which feature actually earns the gap

Method

What an ablation is, and why one run is deliberately expected to do nothing

An ablation turns one thing off and measures what changes, with everything else held fixed. The discipline is that each flag must be paired with a workload where it can act — otherwise the result is a null that means nothing.

Disabling prefix caching under unique prompts is exactly such a null: there are no shared prefixes to hit, so on and off must be identical. That run is included anyway, as a control. If it moved, the harness would not be measuring what it claims and every other number here would be suspect. It came in at +4%, within noise. The control passed, which is what makes the rest trustworthy.

Concept

Chunked prefill

Processing a new request's prompt is one large, compute-heavy pass. If it runs as its own step, every request already streaming stops dead until it finishes — the admission stall our own engine suffered, worth 213 ms of ITL p95.

Chunked prefill splits that pass into pieces small enough to share a step with ongoing decodes. Nobody stalls. It is a latency intervention; it does not create throughput that was not there, and the measurement below shows exactly that.

Chunked prefill buys tail latency, not throughput. Capacity barely moves — 5.79 to 5.66 req/s — but ITL p95 goes from 456 ms to 612 ms without it, 34% worse. I had predicted a 10-20% capacity drop. The prediction was wrong about what the flag does, which is more useful than being wrong about a magnitude.

The fp8 KV result is a second prediction worth stating, because the naive expectation is so tempting: halving the bytes per cached token should roughly double concurrency, and therefore throughput. It bought 11%. The binding constraint here is prefill compute, and quantising the cache does nothing for compute. A 1.57× larger memory budget cannot help a workload that is not short of memory.

Part four · Making the model smaller

Quantization, and the two separate things it buys

Every number so far used the model at full precision: each of its 8.19 billion parameters stored in two bytes, 15.26 GiB in total. Quantization stores them in fewer bits — one byte each (fp8), or half a byte (int4) — accepting some rounding error in exchange for space.

The reason this is worth a whole phase is that it buys two different things at once, and they are easy to confuse:

  • Fewer bytes to read. Every generated token requires reading the entire model out of memory. Halve the model, halve that read. This makes each step faster.
  • Freed memory becomes cache. Whatever the weights stop occupying is handed to the KV cache, which is what limits how many people can be served at once.

The first works always. The second only works if you were running out of cache in the first place — and whether you were depends entirely on what your users are sending. That distinction turns out to be the whole story.

Concept

The card is sold as 24 GB. Almost none of that is available for the thing you care about:

Five. That is the real concurrency limit of a 24 GB card running an 8B model on long requests, and it is four haircuts away from the number on the box. Now halve the weights and watch what happens to the last line: the cache is the small term, so giving it the slack is enormous leverage. fp8 takes it from 26,176 tokens to 73,264, and int4 to 95,648 — 3.7× more people served from the same silicon.

The same flag, worth 1.07× or 2.35×

Part three ended with three failed predictions that shared one shape: each guessed the effect of raising a ceiling without first checking whether anything was pressing against it. This phase was designed to avoid repeating that — and the check it forced changed the entire experiment.

The benchmark used throughout this document sends a 512-token prompt and asks for 64 tokens back. Running the arithmetic before spending any GPU time: at that request size the KV cache sits about 29% full. Quantization's headline benefit is more cache. Tripling something you are using 29% of does nothing.

So the phase was measured on two workloads. The small one above, and a second one shaped like a real question with search results attached — 4,096 tokens in, 1,024 out. Same GPU, same model, same benchmark client, same day:

On small requests the cache was never the constraint, so freeing it achieves nothing and only the faster-reads effect survives. On realistic ones the cache is the entire constraint and the same flag is transformative.

Had this phase been run on the benchmark that was already set up and already working — the obvious, free, sensible choice — it would have concluded that quantization is barely worth the trouble, and been wrong by a factor of two.

Why the prediction still missed

More users means more cache to read, every single step

Both predictions for the large workload were written as 2.5–3.5× and both came in low, for one reason worth understanding. Reading the model is not the only memory traffic in a decode step — the server must also read the cache of every request currently in flight.

              weights    cache read/step   total
bf16   5 users  16.39 GB      3.47 GB       19.86 GB
fp8   14 users   8.19 GB      9.71 GB       17.90 GB
int4  19 users   6.12 GB     12.71 GB       18.83 GB

The step costs almost exactly the same in all three cases. Quantization halved the weights, but the extra users it allowed brought their own caches along and ate the saving. So the gain is not faster steps at all — it is the same 40 ms divided among more people. Concurrency partly limits itself, which the prediction had assumed away.

Grading a model that disagrees with itself

Everything up to this point could only be faster or slower. Quantization is the first change that can make the model worse, and worse in a way no throughput number will ever reveal. So quality had to be measured — which is harder than it sounds, for a reason that catches most people.

Concept

The same model, asked the same question twice, does not always answer the same way

Even with all randomness switched off, the server processes twelve requests together, and which twelve are grouped shifts constantly as requests finish. Different grouping means the GPU adds numbers in a different order, which means tiny rounding differences, which occasionally means a different final answer.

So a quantized model that disagrees with the original on 5% of questions might be damaged — or might be showing you the model's own jitter. There is no way to tell from that number alone.

The fix is to run the unquantized model twice and see how often it disagrees with itself. That is the noise floor. Here it came out at 1.8%, and nothing below it counts as damage. That control run cost 33 minutes and made every subsequent number interpretable; without it the whole quality axis is uninterpretable arithmetic.

The test set was 560 problems per configuration, built rather than downloaded so that the difficulty could be dialled: chains of arithmetic where each step consumes the previous step's answer, at 4, 8, 16 and 32 steps. Nothing can be skipped, so the step count is genuinely a measure of how much sequential reasoning is required.

Measured against the noise floor, int4 costs 2.1 accuracy points overall. That aggregate hides everything that matters:

Zero, three, nine, thirty-seven. The damage grows with the length of the reasoning required, exactly as compounding error should. At 32 steps int4 destroys more than a third of what the full model solved — while the headline figure politely reports two points.

And the last row matters just as much. Retrieval — finding one buried fact among decoys in a long document — was perfect for all three, 270 out of 270, at every depth. The damage is not general. It is specific to multi-step reasoning, and it leaves the thing a search-backed chat app spends most of its time doing completely untouched.

The prediction that was exactly backwards

The project's own written specification contained a confident claim about all this, recorded long before the measurement:

Thinking amplifies it — this is the project-critical one. A reasoning chain is 1,000+ sequential tokens where each conditions the next, so small per-token errors compound.

The logic is appealing. Let a slightly-damaged model reason for a thousand tokens and the damage should snowball. The model used here can have that reasoning switched on or off on identical weights, so the claim was directly testable. On the same 32-step problems:

int4, on problems the full model solvedBroken
Allowed to reason step by step first1%
Forced to answer directly37%

Reasoning does not amplify quantization damage. It absorbs it. Given room to work, the model catches its own perturbed arithmetic and corrects it — the chain is self-repairing, not error-compounding. Denied that room, every rounding error lands straight in the answer.

The specification was updated with the correction written underneath the original claim rather than replacing it. A document that quietly deletes its failed predictions cannot be trusted about its successful ones.

There is a practical consequence, and it is the one that carries into the rest of the project. Thinking tokens are expensive: they occupy cache for as long as they run, so a thinking user costs several non-thinking ones. But an int4 model apparently needs to think in order to stay accurate. The memory quantization frees is partly spent buying back the reasoning that keeps it correct. Those two knobs are not independent, which is a problem for whatever scheduler eventually has to turn them.

Part five · Guessing ahead

The 99.6% of the GPU that does nothing

Every phase so far made the server hold more people. This one goes after a different number: how long one person waits. And it starts from a measurement that sounds like a mistake.

Producing one token means reading all 16.39 GB of the model out of memory. That takes 34 ms. The arithmetic performed during those 34 ms comes to 16.4 billion operations, against a chip that can do 125 trillion per second.

The compute units are 99.6% idle while the GPU decodes. Not busy, not partly used — idle, waiting on memory. Every earlier phase optimised around that wait. This one spends it.

The trick is called speculative decoding, and the shape of it is simple. Something cheap guesses the next few tokens. The big model then checks all of them in a single pass — asking, at each position, "is this what I would have said?" Guesses it agrees with are kept. At the first disagreement, that guess and everything after it is thrown away, and the model's own token is used instead.

The reason this is worth doing is the asymmetry underneath it. A forward pass costs almost the same whether you push one token through it or five, because the cost is dominated by reading the weights, not by the arithmetic. Checking four guesses is nearly free; the expensive part already happened.

Why this cannot make the answer worse

Rejected guesses are replaced by what the model would have said anyway

It is natural to assume that anything called "speculative" trades accuracy for speed. It does not. Where the guess matches, the output is what the model would have produced. Where it does not, the guess is discarded and the model's own token takes its place. Either way you end up with the model's answer — just sooner.

That is the theory, and this document does not take theory on trust. It was measured, at the end of the phase, on 1,210 items. The result is in the last section.

The number that governs everything is the acceptance rate: what fraction of guesses survive the check. It is not derivable from hardware specs — it depends on the guesser, the model, and, as it turned out, very heavily on what is being written.

The helper has to live somewhere

The guesser used here is a small trained component called an EAGLE head. It is not a smaller language model; it is a single layer trained specifically to imitate this model, and it gets to see the big model's internal state rather than only its text. That is what makes it guess well.

Before renting the GPU, its size was worked out from its configuration file: 622M parameters of vocabulary lookup, 193M for its one layer, 131M for its output head, 50M for the part that reads the big model's state. Just under a billion parameters, 1.904 GiB. The actual file is 2,044,116,968 bytes. The estimate was right to 2%.

That produced the phase's first surprise, and it is worth pausing on because it inverts the intuition. The "one-layer head" is bigger than a real small model. Qwen3-0.6B — twenty-eight layers, a genuine miniature language model — is 1.400 GiB. The head is larger because it carries a lookup table covering all 151,936 possible tokens, and that table is most of its bulk. One layer describes how much arithmetic it does, not how much room it takes.

And room is the thing in short supply. The helper lives in the same memory as the KV cache — the scratchpad that lets the server hold conversations in flight. Every gigabyte it takes is conversations the server can no longer hold. So the prediction was straightforward: the cache should shrink by exactly the helper's size, 13,863 tokens' worth.

Quantization is what makes guessing affordable

This is Part four's finding arriving from the opposite direction. There, memory freed became capacity gained. Here, memory spent becomes capacity lost — and how much it hurts depends entirely on how much you had. The two phases combine into a claim neither could make alone.

A number that would have been a false headline

Text repetition scored 0.93, and it meant almost nothing

On the filler benchmark, the no-model guesser reported an acceptance rate of 0.9333, against the trained head's 0.3035. Read plainly, that says the free option is three times better.

The catch is in what acceptance measures. It is conditional on a guess having been made, and text repetition only guesses when it finds a matching phrase to copy — which happened on 4.4% of steps. Right 93% of the time, on one step in twenty-three. The real gain was 1.12×, not 3×.

It is the same species of error as the token-counting bug in the next section: a measure whose definition quietly assumes something the new mechanism breaks. Comparing a conditional rate against an unconditional one produces a confident, plausible, entirely wrong answer.

Does the answer change?

All of the above is worthless if guessing quietly alters what the model says. So the whole thing was run twice more, with and without guessing, over 1,210 graded items — and compared against a floor established in the previous phase, where the model was run against itself to find out how much it disagrees with its own answers just from the order arithmetic happens to be performed in.

Accuracy 89.3% without guessing, 89.9% with. Answers differed on 2.8% of items; the model's disagreement with itself is 1.8%. Statistically indistinguishable. Guessing fixed 17 items the control got wrong and broke 10 it got right — a net in its favour, and noise either way.

The shape of the disagreement is better evidence than its size. Three whole categories reproduced identical answers on every single item — natural reasoning, thinking-enabled arithmetic, document recall. All of the disagreement piled into one category: the hardest arithmetic without a thinking block, where the model scores 44% and is barely better than guessing. There, any perturbation flips answers.

If the mechanism were subtly broken, errors would be spread everywhere in proportion to how much text was generated. Instead they appear only where the model was already unsure. That is the signature of ordinary nondeterminism, not of a technique quietly changing the answer — so every speed-up above is a speed-up of the same model, not a faster different one.

Part six · Where the crossover really came from

The inversion was never about guessing

Part five ended on a clean-looking result: guessing ahead is a large win at 2 requests a second and a large loss at 6, so somewhere in between it inverts. The explanation offered there was the textbook one — on a busy server the checking work stops being free, because the GPU no longer has idle capacity to spend. That explanation is wrong, and the way it was caught is the point of this part.

Concept

Running out of cache does not make requests slow, it makes them wait

Every conversation being served holds its own KV cache for as long as it is in flight. The server admits new requests only while there is room for their cache. When there is not, the request does not run slowly — it does not run at all. It sits in a queue until somebody finishes and releases their space.

This matters for diagnosis because both causes produce the same symptom. Verification overhead would make each step slower. Cache exhaustion makes steps take exactly as long as before, and inserts a wait before the work starts. Averaged into one latency number the two are indistinguishable, which is why the wrong explanation survived a whole phase.

The engine had been reporting which of the two it was, every ten seconds, into a log nobody had read. It records how full the cache is and how many requests are waiting:

A server that cannot hold one maximum-length conversation does not start. Without quantization there is nothing to measure.

Everything measured so far treats requests as independent. A chat is not: turn 25 resends all of turns 1 through 24 before adding anything new. That makes it the ideal case for prefix caching, which Part three measured as worth nothing on traffic where every request differs.

Both things can be true, and the gap between them is large. One conversation was grown to 25 turns and measured twice. The control failed twice first

A control that does not control produces a null result that reads as a finding

The first two attempts at this measurement returned the two curves lying on top of each other — 1.0× apart, against a prediction of roughly 21×. Read plainly that says prefix caching is worth nothing in a conversation, which would have been a genuinely surprising result and was entirely an artifact.

The random text had been attached to the new user message at the end of each turn. But the conversation history is rendered before that message, so every token up to it still matched what was cached, and the cache hit exactly as it did in the warm run. The arm intended to defeat the cache was not touching the part of the prompt the cache reads first.

The fix was to move the random block to the very front. The lasting fix was to make the control prove itself: it now reads the engine's own report of how much of the prompt it recognised, checks it at turn 3, and refuses to collect data if the cache is hitting. It measured 0.000 across all 25 turns. A control that cannot demonstrate it is controlling is worse than no control at all, because its null result looks like knowledge.

That left one arm proving itself and the other not: the warm run had recorded no cache figures at all, so "the cache was working" was an inference from its flat curve rather than a recorded fact. The pair was therefore run again, on one server with both arms reporting. The warm arm goes 0.000 at turn 1 to 0.957 by turn 25; the cold arm holds 0.000 throughout. The separation reproduced at 13.76× against the original 13.83×, and the cold curve landed on the same 2,290.8 ms at turn 25 both times.

A correction to Part four

The noise floor belongs to the question set, not to the model

Part four established that the model disagrees with itself 1.8% of the time, and used that as the threshold below which nothing counts as damage. Part five tested against the same 1.8%, legitimately, because it reused the same questions.

Running the identical configuration against itself on a harder mixture of questions gives 7.8%. The disagreement concentrates exactly where the model is near the edge of what it can do: 25.7% churn on a category it solves about two thirds of the time, and 0.0% both where it scores 100% and where it scores 0%. A model that is sure of an answer gives the same one twice; a model that is guessing gives a different one.

So the floor is a property of what you asked, not of the model, and carrying a floor between experiments with different question sets is invalid. This document did that once and the claim it supported has been withdrawn. The 1.8% figures in Parts four and five stand, because those experiments measured their own floor on their own questions.

What a person actually waits for

Every part so far measured the engine. This one measures the thing built on top of it: a chat application that searches the web before answering. Four tokens that made every conversation 2.3× slower

A chat is not a series of independent questions. Turn 30 re-sends the whole conversation, about 9,300 tokens, before adding anything new. Part three showed the engine can skip re-reading text it has already processed, which is what makes long chats survivable at all. So the layout of that prompt is the single most important thing about a chat product.

Something was quietly breaking it. Reading the engine's own report of how much of each prompt it recognised, the answer was always the same: everything up to the previous reply, and nothing after. The model's own last answer was being re-read from scratch every single turn.

The mechanism

An empty box that appears in one place and not the other

This model can be asked to reason before answering, or to skip it. When reasoning is switched off, its prompt format inserts an empty pair of thinking markers — <think></think>, nothing between them — into the prompt the model is asked to continue.

But when that same turn is later replayed as history, the markers are left out. So the text of turn 29, as rebuilt during turn 30, is not what was actually sent during turn 29. It differs by four tokens, near the end. Matching stops at the first difference, so everything after those four tokens is thrown away and recomputed.

Rendering the prompts offline, without a GPU, made it exact: the stock format broke the match at 5 of 5 turn transitions, and a corrected one at 0 of 5. On the real server the correction is worth this:

Two experiments that came back as bugs

Two measurements were designed to settle product decisions. Neither did. Both instead found a defect, which is the more useful outcome and worth showing rather than tidying away.

Should the model's old reasoning be kept in the conversation?

Reasoning text is long, and keeping it makes the history grow much faster. Before the formatting fix, keeping it looked 2.4× slower, which reads like a clear product decision. After the fix:

reasoning stripped   74.3 ms      reasoning kept   74.3 ms

Identical. The entire difference had been the formatting bug, appearing in one arm and not the other. There was no tradeoff to decide; there was a defect to fix. The project's own specification had written this up as a decision to be measured.

What to do when a conversation outgrows the window

Eventually a chat is too long to send. Two options: drop the oldest messages, or compress them into a summary and keep that. Dropping should be terrible, because removing text from the front shifts the position of everything after it and nothing matches any more. Summarising should be good: one expensive turn, then a new stable opening the engine can recognise again.

But the summary written here embedded a count of how many messages it had replaced, and that count rises every turn. So the summary text changed on every single request, the match broke at the very start of the prompt, and the clever strategy performed within 5 ms of the naive one it was meant to beat.

That is a bug, not a result, and it took four attempts to fix — three of which were caught by a check that runs on a laptop in a second, asserting the summary text holds steady from turn to turn. The first fix changed nothing because the code recomputes the boundary from the whole conversation every turn, so it advanced one message pair at a time no matter what. The second left a clamp that collapsed whenever fewer than a block of messages remained. The third was a second piece of code deciding the same boundary and fighting the first.

The shape that finally works advances the summarised boundary in jumps rather than continuously, so the same text is reused for many turns at a stretch. Measured again with that in place:

The periodic spike is not overhead either. At each re-summarisation the conversation is trimmed to about 2,924 tokens and re-read from scratch, and at the cost-per-token measured three parts earlier that predicts 852 ms against 817 measured. The same constant, taken in a different experiment weeks before, lands within 4% on a number it was never fitted to.

The general rule is worth more than the bug: summarising only helps if the summary is identical, character for character, from one turn to the next. Regenerate it each turn — from a counter, a timestamp, or a fresh model call that varies at all — and the entire benefit is given up while still paying to produce it.

The mistake underneath four of these

Four measurements in this part first came back as clean, confident nulls. No cache contention as conversations pile up. No difference between the two overflow strategies. Every configuration equally bad under load.

All four were wrong in the same way, and none of them were wrong predictions. The experiment never entered the range where the effect it measures exists. The contention test ran 4% past the limit where contention begins. The overflow test used a conversation that never actually overflowed. The load test used arrival rates already past the point where everything fails equally.

Why this appeared now

A protocol that was complete for five parts and not for the sixth

Every number in this document was predicted in writing beforehand. That discipline asks one question: what will the number be? For Parts one through five it was enough, because those measured things that exist wherever you point the instrument — how fast tokens come out, how much memory the weights take.

This part measures thresholds. Cache contention only exists past the cache's size. An overflow strategy only exists past the window. Saturation only exists near capacity. Outside those ranges you do not get a wrong number, you get a confident null — and a confident null reads exactly like a finding.

The fix was to stop relying on remembering. The measurement runner now states what each experiment must cross and what its configuration actually produces, and refuses to run when the two do not line up:

contention   needs to exceed   69,264   this config  148,944   2.15×   OK
cold open    needs to stay under 16,384   this config   15,064   0.92×   OK
overflow     needs to exceed   16,384   this config   25,760   1.57×   OK

Fed the original broken settings, it refuses them: 0.59× REFUSED. It also refused the first attempt at a fix, at 1.28×, as too close to the boundary to observe anything after it — which is how the overflow test ended up at 160 turns rather than 130. That is the same move as every other guard in this document: the benchmark that validates itself against a fake server, the control that reads the engine's counters before trusting its own null. Written rules did not survive the sixth hour of a session; the ones that hold are the ones a program checks.

Part eight · Thinking as a scheduling knob

The reasoning nobody was waiting for

A reasoning model spends its first several seconds writing a hidden thought the user never sees. On this hardware that is not a detail — it is most of the wait. So the question is whether that silence buys anything, and it is answerable: this model exposes a cap on how many reasoning tokens it may spend, and the cap can be swept.

Seven settings from zero to unbounded, on grade-school word problems, run twice for 400 graded answers per setting:

0.4 points for a 160× cut in silence. Turning thinking off entirely costs 0.4 points against letting it run — and 0.4 points is inside the ±2 the repeat-run control puts on this sample. On these questions the hidden reasoning trace buys nothing measurable and costs the user nearly eighteen seconds.

There is a second argument for a cap that has nothing to do with the average. Between two identical runs the unbounded setting scored 95.8% and then 91.5%, while every capped setting moved at most one point. The answers were not the unstable part — accuracy among replies that finished was 96.8% and 95.8%, a point apart. What moved was how often a reply ran away and never finished at all, and that rose from 1.0% to 4.5% purely because the ceiling had been raised from 3,000 tokens to 4,096, letting a runaway run further before being cut off. A budget does not only cut latency. It caps variance, by removing the request that thinks until it is killed and returns nothing.

Halfway is the worst place to stop

The same sweep on harder competition-style problems does not produce the same flat line. It produces a trough, and the trough is deep:

A middling budget is 11.1 points worse than a tiny one. Give the model room or give it almost none; the setting in between is the one to avoid. The same shape appeared at 11.6 and 11.1 points in two earlier runs, so it is not a sampling accident.

Read the label on the box

Four parts of this document used a setting the model's own card forbids

Everything from part four onward sent temperature 0 — greedy decoding, the obvious choice for a reproducible measurement. The Qwen3 model card says, twice, not to: "DO NOT use greedy decoding, as it can lead to performance degradation and endless repetitions." That warning names precisely the runaway tail the previous section attributes to unbounded reasoning.

So the trough was re-measured under the vendor's recommended sampling, because if it vanished the finding had to be withdrawn rather than amended. It did not vanish; it deepened. The comparisons survive because every setting shared the configuration. The causal story about unbounded reasoning does not fully survive, and the honest correction is that the vendor documented the failure mode before it was ever measured here.

One surprise came back with it. Three greedy measurements of the same 1024-token setting read 82.8, 83.3 and 88.9 — a six-point spread at identical configuration, twice the noise floor. The single measurement under the card's sampling landed at 82.8. Greedy is supposed to be the deterministic setting and behaved as the erratic one, which is what a per-item coin flip between repeating and not repeating looks like when averaged over 180 problems.

It is not how long it thinks. It is where you cut

A trough needs a mechanism, and the records carry one. Split every capped answer by a single question: at the moment the cap bit, had the model already reached an answer inside its own reasoning?

After it had an answer68–70%91.0%92.3%

Interrupted before it reaches an answer, the model scores a coin flip — twice, 53.2% then 51.1%. Interrupted after, it scores 91 to 92%. The budget is not a dial on quality. It is a bet on whether the cut lands past the model's natural solution length, and a middling budget is simply the setting that loses that bet most often.

That also explains why a very small budget is safe. Cut at 128 tokens and the model has barely started, emits its reasoning-closing tag, and then re-derives the whole solution in the open where the grader can see it. The answer still gets computed; it just gets computed visibly. The danger zone is the middle, where there is enough hidden work to look complete and not enough to be complete.

Forty-two points of politeness

Cutting a thought off requires putting words in the model's mouth. Qwen's own technical report gives the phrase it was trained to accept: "Considering the limited time by the user, I have to give the solution based on the thinking directly now." The obvious alternative is to say nothing at all and just close the tag. Two servers, identical but for that string:

The vendor's own interrupt phrase costs 42.7 points at a small budget. The prediction said it would be worth zero to five points in its favour, on the reasoning that the model was trained on that exact sentence. It was, and that is the problem.

The phrase is an instruction, and the model obeys it. "Give the solution based on the thinking directly now" is a command to answer from whatever partial state exists — which forbids exactly the recovery that makes small budgets safe. One record was cut mid-sentence and did as it was told:

...Day 1: 78 - 39 = 39.\n\nDay 2[Considering the limited time by the user, I have to
give the solution based on the thinking directly now.\n</think>]  →  ".\n\nANSWER: 18"

It stopped mid-"Day 2", was told to answer immediately, and answered — wrongly, from three lines of arithmetic it had not finished. The general statement: a trained interrupt designed for "you are out of time, wrap up" is correct when the thought is nearly complete and destructive when it has barely started. It is safe only where the budget already lands past the model's natural solution length, which is precisely where it makes no difference at all.

The clever policy lost to the simple one

If a small budget is cheap and a large one is occasionally worth it, the obvious system is a policy that watches the queue and switches: spend 2048 tokens while the server is quiet, drop to 128 when the backlog grows past eight, return only when it falls below two. That policy was built, and measured against the two fixed settings it switches between, under the same offered load.

The fixed small budget beats the adaptive policy on both axes — 95.0% against 94.4%, and 11.1 s of silence against 48.1 s. There is no trade being made. The clever thing is simply worse than the dumb thing it was built to improve on.

The reason is queueing, not modelling. Under sustained overload the backlog is deep almost all the time, so the policy issues the small budget on 74% of requests anyway. The other 26% are 2048-token requests that each occupy one of only sixteen sequence slots for about two minutes. Those requests do not merely cost themselves latency — they hold slots that the cheap requests behind them need, so the whole queue drains slower. The policy pays the full latency price of the expensive setting on a quarter of its traffic and buys 0.6 points of accuracy with it, which is inside the noise. The hysteresis does not save it; the hysteresis is what lets it sit at the expensive setting long enough to do the damage.

One caveat is load-bearing, and it is the experiment that could still rescue the idea: this is one constant arrival rate. An adaptive policy exists to handle load that varies, and a constant offered load tests only its behaviour in permanent overload. A bursty pattern where the queue genuinely empties between bursts is a different question and was not asked here.

The other scheduling knob is ranking: mark a request urgent and have the engine serve it first. Matched pairs of identical requests, one marked high and one low, fired into a backlog held open by a separate load generator.

The first run set priorities, got a clean null, and the null was the scheduler discarding them — 33.63 s against 33.65 s, which is two requests being treated identically, not a weak effect.

With the flag on and a genuine backlog, priority moved a request from 178 s to 31 s. With a shallow backlog that drains in about a second there is nothing to reorder and the effect is exactly zero, which is the same shape as every other result in this document: the technique has no number, only a number given something pressing against the limit it relieves. The honest weakness is that the 5.7× rests on a single valid pair; the other pairs in that run fired with no backlog, where priority cannot act by construction.

A six-second win that was not the search

The last experiment is the one the whole gateway existed for. When an answer needs a web search, the search is a round trip the user waits through. But a reasoning model has something to do during that wait: it can start thinking against the un-retrieved question, and the results can be spliced into its own half-finished thought when they land. Three orderings, on 67 real questions a search engine actually answers.

Six seconds faster, same accuracy. It reads as a clean win for overlapping, and it is not one.

The overlapping arm produced 55 tokens where the baseline produced 236. At its own measured decode rate of 46.6 ms per token, those 181 missing tokens are worth 8.4 seconds — more than the entire six-second gap. The search round trip actually available to hide was 753 ms. The arithmetic leaves no room for latency-hiding to be the cause.

What happened instead is that splicing results into a running thought interrupts it. The cue reads "Wait, the search results just arrived… I should use these to answer", and the model does exactly that: it stops reasoning and answers. This is part eight's first finding arriving by a different road — the thinking it skipped was worth nothing, because accuracy is identical either way.

One prediction in that run was right for the right reason, and it is the one worth keeping. First-token time was predicted to improve by 700 to 1000 ms, on the grounds that the baseline must read a 3,000-token block of search results before it can say anything, at a cost-per-token measured two parts earlier: 3,000 × 0.2915 ms = 875 ms. Measured: 882 ms. Agreement to 0.8% on a constant taken from an unrelated experiment weeks before — and note what it means. Overlapping does not hide the search from the first token either. Both orderings wait for it. What overlapping buys is that it has already done the reading.

The third ordering is the cautionary one. Thinking first and searching afterwards costs almost nothing end to end — 172 ms — but 8.3 seconds at the first token, because the relay runs the entire first generation before it starts the search. Ordering is nearly free in total time and decisive in the only latency a person actually perceives.

The bugs, and why the method caught them

Every measurement was preceded by a written prediction with its arithmetic. That is not ceremony — it is the only thing that makes a wrong number visible. A selection of what it caught:

  • A missing torch.inference_mode() made the engine build a training graph on every forward pass and run out of memory at 21.7 GiB on a workload needing 16. Sixty-seven passing tests against a mock could not see it — a fake tensor library has no autograd to leak.
  • .generate() silently applies a repetition penalty even under greedy decoding. Left in place, the correctness gate would have failed on a difference that was not a bug in our code.
  • Warming up at the wrong shape warms nothing. A 6-token warmup before a 412-token measurement left a 36% outlier on the first run, because the GPU selects kernels per problem shape.
  • A sweep's step size is the measurement's precision. Testing batch 4 and 8 gives an answer with ±3 error bars — which is how "dies above 4" entered the record when the truth was 7. The same mistake was then repeated in our own sweep.
  • vLLM's KV cache size varies 28% between identical launches, because it profiles free memory at startup. A capacity difference between two configurations is not attributable to a flag until their budgets are confirmed equal — an ablation was re-run with memory pinned for exactly this reason.
  • The grader was defeated by the model agreeing with it. The quality harness reported 84% accuracy with 16% of replies unreadable — and zero replies that were readable but wrong. Those two facts together are the diagnosis: every answer the model gave was correct and the grader could not find them. It was writing \boxed{72}, its trained habit, rather than the format demanded of it. Quantization changes formatting, so a version reaching for that habit slightly more often would have scored lower for reasons having nothing to do with reasoning.
  • A pattern that swallowed a newline. The model put its answer under a Final Answer: heading; the pattern matched the heading itself, consumed the line break and captured the following line whole. Correct answers scored as unreadable with the right number sitting one line below. Both grading bugs were repaired and every saved reply re-scored offline at no GPU cost, because the harness had been built to write out the full text of every answer for exactly this eventuality.
  • 22% of requests died mid-answer, and the first diagnosis was wrong. Long streaming requests were failing, which was blamed on the network before checking — and the data contradicted that within one query: four-minute requests failed 1% while thirty-second ones failed 36%. The real cause was connection reuse under fast turnover. It is this section's own lesson turned on its author: state a cause only after testing it against the evidence already in hand.
  • The benchmark counted chunks and called them tokens, and it inverted the headline. For four phases the server sent one token per network message, so counting messages was counting tokens. Guessing ahead sends a whole accepted run in one message, so the count came in low by exactly the speed-up — and the tool reported the technique as 1.5× slower when it is 1.43× faster. Nothing crashed and every figure looked reasonable. What exposed it was not the timing but the word count: the control produced exactly its maximum on every request while the guessing runs produced half as much, and at zero randomness a technique that changes nothing cannot halve the amount of text. A second instrument then rebuilt the true count from an unrelated source and landed on it exactly.
  • An out-of-memory crash the server's own memory check could not see. The verification step briefly builds a scratch buffer sized by the concurrency limit, the guess depth and the vocabulary — 594 MB at the defaults. That allocation happens after the server has measured free memory and sized its cache to fill the GPU, so the server starts, reports itself healthy, and dies on its first request. Whether a given launch survives is decided by how much slack the startup measurement happened to leave. Worse, the default concurrency limit was 256 on a machine that can hold at most 17, so it was reserving 594 MB for a crowd that could never arrive — taken out of the cache, making the real limit lower still.
  • A rate that looked like a count. While testing the acceptance meter against plausible alternative metric names, a series measuring an average was matched by a pattern meant for a total, and would have been added to a token tally. No error — just an acceptance rate a few tenths too high. Found by testing the tool against names it had never seen, before it ever touched the real server.
  • An accuracy column that was a truncation rate. Three reasoning settings scored 56.5%, 56.0% and 52.5% and were written down as a finding about budgets. They were a finding about a token ceiling: 44 to 47.5% of replies hit it, and the 69 that never closed their reasoning scored zero, because a reply cut off mid-thought has no answer to grade. Among replies that finished, all three scored 99–100%. The settings differed only in how often the cap bit. Every run now reports accuracy beside its truncation rate, and any run whose reply-length p95 sits on the ceiling is unusable for an absolute number.
  • A field that had been renamed out from under the client. Turning on the reasoning parser routed every reasoning token into a field the measurement client did not read, because the server had renamed it one version earlier. Accuracy stayed valid, so the arms looked fine — but “time to first token” quietly became time-to-first-visible-token for 89% of records and time-to-first-token for the 11% whose tags leaked, two different quantities averaged together inside one column. Enabling a feature can activate a client bug that was harmless while the feature was off.
  • A control that did not perturb what it claimed to. A cold-cache comparison prefixed random noise to the user’s new message — but the conversation history renders before that message, so every earlier token still matched and the cache hit normally. Warm and cold came out identical against a predicted 21×. A control that does not move the thing it names is worse than no control: it returns a null that reads as a finding.
  • An actuator that was never wired up. The gateway’s budget policy set the flag that enables thinking and never forwarded the budget itself, so every budget it chose was a no-op. Caught by a test asserting the value reaches the outgoing request — without it the policy experiment would have returned three identical arms and concluded, reasonably and wrongly, that the policy does nothing.
  • The right answer for the wrong reason is more dangerous than a wrong one. The prediction tool guessed 7.08 concurrent requests and measurement said 7 — but its safety margin only coincidentally equalled the fragmentation and activations it does not model. Trusting that match would have broken silently the moment any term changed.

The pattern across all of them: bugs that raise exceptions are cheap. Bugs that produce plausible numbers are the ones that quietly destroy work like this.
